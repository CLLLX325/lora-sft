# 中文工单结构化抽取（LoRA 微调 Qwen2.5-0.5B-Instruct）

把客服工单的自由文本，抽成一条固定格式的 JSON：

```json
{
  "category": "退款",
  "sentiment": "负面",
  "escalate": true,
  "entities": {"order_id": "A2007", "product": "空气炸锅", "amount": 399.0}
}
```

## 为什么做这个

下游系统（工单路由、质检看板、客服绩效）要的是结构化字段，不是一段话。
三条常见路线：

| 路线 | 问题 |
| --- | --- |
| 正则 / 关键词 | 中文表达太散，"这单我不想要了"和"申请退货"要写两套规则，维护不住 |
| 调大模型 API | 效果好，但每条工单都要走一次网络，成本和延迟都不可控 |
| **小模型 + LoRA 微调** | 本地跑、单卡训练十分钟、参数只有 4MB，效果够用 |

这里走第三条：0.5B 模型 + LoRA，在一张 RTX 4060 Laptop（8GB）上 137 秒训完。

## 数据

`data_gen.py` 用 **43 个模板** 造样本，按 `模板` 分组切成 train 600 / val 150 / test 150：

```
python data_gen.py
```

**关键设计：训练集和测试集的模板完全不重叠。** 如果随机切分，同一个模板会同时出现在
训练和测试里，模型只要记住"这个句式对应哪个类目"就能拿高分，测出来的数字没有意义。
按模板切分后，测试集里的句式模型一次都没见过，考的是"能不能把没见过的说法映射到见过的字段"。

字段设计：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `category` | 枚举 6 类 | 退货 / 退款 / 换货 / 物流 / 发票 / 其他 |
| `sentiment` | 枚举 3 类 | 正面 / 中性 / 负面 |
| `escalate` | bool | 是否需要升级到人工主管 |
| `entities.order_id` | 字符串 | 形如 A2007，抽不到为 null |
| `entities.product` | 字符串 | 商品名 |
| `entities.amount` | 浮点 | 金额，抽不到为 null |

## 训练

```bash
# 基座模型放在 ./models/Qwen2.5-0.5B-Instruct，
# 或者用环境变量指定：set BASE_MODEL=D:\models\Qwen2.5-0.5B-Instruct
python train_lora.py
```

配置：LoRA `r=8 / alpha=16 / dropout=0.05`，作用于 q、k、v、o 四个投影矩阵；
fp16、3 epoch、batch 2 × 梯度累积 8、lr 2e-4。

| 指标 | 数值 |
| --- | --- |
| 可训练参数 | 1,081,344 / 495,114,112（**0.22%**） |
| 训练耗时 | 137 秒（RTX 4060 Laptop 8GB） |
| train_loss | 0.0229 |
| eval_loss | 0.0375 |
| adapter 体积 | 4.2 MB |

两个容易踩的点写在代码注释里：
1. `labels` 只保留 assistant 回答部分，prompt 段置 `-100`，否则模型会去学"复述用户问题"。
2. 答案末尾要拼 `eos`，模型才知道什么时候停。

## 评测

```bash
python evaluate.py --tag base     # 基座，不挂 adapter
python evaluate.py --tag lora     # 挂 lora-out 里的 adapter
```

逐字段比对，分类字段算 macro F1，抽取字段算精确匹配（金额允许 0.01 误差）。

### 结果（测试集 150 条）

| 字段 | 基座 | LoRA | 提升 |
| --- | --- | --- | --- |
| JSON 合法率 | 100.0% | 100.0% | — |
| category | 58.0%（F1 0.482） | **86.0%**（F1 0.760） | +28.0 |
| sentiment | 68.0%（F1 0.670） | **82.0%**（F1 0.810） | +14.0 |
| escalate（F1） | 0.460 | **0.926** | +0.466 |
| order_id | 97.3% | 100.0% | +2.7 |
| product | 38.7% | **100.0%** | +61.3 |
| amount | 14.7% | **100.0%** | +85.3 |
| 八个字段全对 | 0.0% | **64.7%** | +64.7 |

## 三个结论（比数字本身更重要）

**1. 基座的 JSON 合法率本来就是 100%。**
说明 0.5B 这个尺寸不缺"格式遵从"能力——prompt 里说清楚要 JSON，它就能吐合法 JSON。
微调要解决的是"内容填对"，不是"格式对"。所以这里的评测必须分字段算，
只报"JSON 合法率"等于自己骗自己。

**2. escalate 的 F1 从 0.460 涨到 0.926，是提升最真实的一项。**
"要不要升级"没有字面线索（"我要投诉"不一定升级，"你们太慢了"反而可能升级），
只能从语义判断，正是微调擅长、规则不擅长的地方。

**3. product / amount 到 100% 要打个折扣看。**
这两个字段基本是"把原文里的实体抄出来"，任务本身偏简单。真实工单里会有错别字、
口语简称、一句话多个商品，那时不会这么高。讲这个项目时我一般主动说明这一点，
而不是拿 100% 当卖点。

## 剩余 35.3% 的"全对"失败在哪

主要是 `category` 的边缘样本：一句话里同时提到退款和发票、或者"换货"和"退货"的边界。
这类歧义是标注体系本身的问题（人也未必标得一致），不是模型能力问题——
下一步该做的是明确标注规则，而不是加数据量。

## 局限

- 数据是模板合成的，真实工单的噪声（错别字、语音转写错误、超长文本）没有覆盖。
- 只验证了 0.5B，没有和 7B + 4bit QLoRA、或大模型 API few-shot 做对比。
- 单卡单次运行，没做多种子平均，0.0375 的 eval_loss 有随机性。
- 评测只看单条样本，没有做端到端（工单进来 → 落库）的集成测试。
